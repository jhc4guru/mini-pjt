# DECISIONS.md

이 프로젝트의 **중요한 결정과 그 이유**를 모아 둔 문서. 요구사항(`SERVICE.md`)과 규칙(`CLAUDE.md`)이 "무엇"이라면, 여기는 "왜 그렇게 정했는가"다.

## 사용 규칙
- 정책, 구조, 방식을 정하거나 바꿀 때 항목을 추가한다. 항목마다 **결정, 이유, 검토한 대안, 결정자, 재검토 조건**을 쓴다.
- 결정을 번복하면 이전 항목을 지우지 않고 상태를 `대체됨`으로 바꾸고 새 항목을 만든다. 번복 이력은 맨 아래 표에도 한 줄 남긴다.
- **결정자 표기:** `사용자`(사용자가 직접 정함) / `제안→승인`(Claude가 제안하고 사용자가 승인) / `Claude 판단`(위임받아 측정·검토 후 정함. 사용자가 아직 검토하지 않았을 수 있음).
- **상태:** `확정` / `제안`(미확정) / `대체됨`.
- 근거가 측정이면 어디서 쟀는지 적는다. 근거가 사용자 발언이면 요지를 인용한다.
- 날짜는 별도 표기가 없으면 2026-11-04.

## A. 제품과 흐름

### D-01. 승인 후 서버가 실행하고 결과를 둘이 공유
- **결정:** 모델이 계획과 명령을 만들고, 사람이 승인하면 서버가 실행하며, 결과를 두 사람이 같은 화면에서 본다.
- **이유:** 사용자 요구가 "반복 작업(작업 계획 생성, cmd 작성)을 모델로 자동화하고, 사람이 확인 후 실행"이었다. 실행까지 서버가 맡아야 결과 공유와 이력(감사)이 가능하다. 단순 복사 방식은 실행 결과가 시스템 밖에 남는다.
- **검토한 대안:** (a) 명령 텍스트만 만들고 사람이 복사 실행, (c) 읽기는 자동·변경만 승인.
- **결정자:** 사용자 — "b 로 가자. 승인하면 서버가 실행하고 결과를 둘이 같이 보는 방식으로."
- **예외:** 서버가 실행할 수 없는 명령은 D-06(`manual`).

### D-02. 4-eyes 승인, 읽기/변경은 규칙으로 분류
- **결정:** 변경 명령은 요청자가 아닌 사람이 승인한다. 읽기(describe/list/get)는 요청자가 바로 실행한다. 읽기/변경 분류는 문서의 허용 목록 규칙으로 하고, 애매하면 변경으로 취급한다.
- **이유:** 2인 1조 작업의 목적이 상호 검증이다. 분류를 모델 판단에 맡기면 모델 오류가 곧 승인 우회가 된다. 규칙이면 결정적이고 테스트할 수 있다.
- **검토한 대안:** 역할 분리(요청자/승인자 고정), 자유형(아무나 승인), 모든 명령에 승인.
- **결정자:** 사용자(4-eyes), 제안→승인(읽기/변경 규칙 분류).

### D-03. 링크 초대 + 닉네임, 로그인 없음
- **결정:** 링크로 세션에 초대하고, 입장 시 닉네임을 입력해 사용자를 구분한다. 로그인은 없다.
- **이유:** Phase 1은 로컬 검증이고 인증 인프라가 없다. 사용자 구분은 필요하다(4-eyes 때문).
- **한계:** 닉네임은 자기 신고라 실제 운영에서는 4-eyes를 보장하지 못한다.
- **재검토 조건:** 실제 AWS 연동(Phase 3) 전에 사내 SSO 등 실제 인증으로 교체.
- **결정자:** 사용자 — "로그인은 없어도 될것 같긴 한데 사용자 구분은 필요해."

### D-04. 자격증명 없이 mock 실행 (moto + kubectl 고정 응답)
- **결정:** 실행기는 인터페이스로 분리하고, 지금은 moto 서버(AWS API 모사)와 kubectl 고정 응답을 쓴다. mock 모드에서는 엔드포인트와 더미 키를 강제로 덮어써 실제 AWS로 나가지 않는다.
- **이유:** 사용자가 "AWS 자격증명은 없이 이후 추가 개발에서 진행, 로컬에서 mock 테스트"를 원했다. `.env`에 Bedrock용 실제 키가 있어 실행기가 이를 상속하면 실제 AWS로 나갈 위험이 있어 환경을 분리한다.
- **한계:** moto의 EKS는 메타데이터만 지원하고 쿠버네티스 API가 없어 kubectl은 moto로 안 된다(고정 응답으로 대체).
- **결정자:** 사용자(moto 제안), 제안→승인(kubectl 고정 응답, 환경 분리).

## B. CLI 처리 방식 (핵심)

### D-05. CLI 지식은 직접 작성한 문서, 모델은 문서 근거로 명령을 도출
- **결정:** AWS CLI와 kubectl 지식을 `knowledge/cli/`에 마크다운으로 직접 작성해 저장하고, 모델은 사용자 입력을 해석한 뒤 이 문서를 검색해 근거를 두고 명령을 만든다. 화면에 근거 문서를 함께 보여준다.
- **이유:** 사용자가 "가장 중요한 것"으로 꼽은 요구다. 모델의 기억에만 의존하면 존재하지 않는 옵션을 지어낼 수 있다(환각). 문서 근거가 있으면 승인자가 검증할 수 있고, 출력 가드가 문서와 실제 CLI로 기계 검증할 수 있다.
- **검토한 대안:** 문서를 통째로 프롬프트에 넣기(문서가 늘면 불가), 공식 문서 수집(양이 많고 범위 제한 필요).
- **문서는 실제 CLI와 대조해 검증한다:** `tests/check_docs.py`가 명령·옵션이 `aws`/`kubectl` 도움말에 실제로 있는지 확인한다. 이 검증이 문서 오류를 실제로 잡았다(`terminate-instance-in-auto-scaling-group`의 대상 지정 방식 등).
- **결정자:** 사용자.

### D-06. 명령 종류: `read` / `mutate` / `manual` (manual은 서버가 실행하지 않음)
- **결정:** 모든 명령에 종류를 붙인다. `read`는 조회, `mutate`는 변경(4-eyes 승인 후 서버 실행), **`manual`은 명령 문구만 보여주고 사람이 자기 터미널에서 직접 실행**한다. 서버 실행기는 `manual`을 거부한다(폴백 포함). 대상: `kubectl exec/attach/port-forward/cp/proxy/debug/edit`, `aws iam create-access-key/create-login-profile`.
- **이유:**
  - `exec`, `attach`, `debug`: 대화형이거나 임의 명령을 실행해 계획·승인 모델로 통제할 수 없다.
  - `port-forward`, `proxy`: 종료되지 않는 연결이고 내부 서비스를 서버 밖으로 노출할 수 있다.
  - `cp`: 서버 파일 시스템을 건드린다.
  - `create-access-key`, `create-login-profile`: 시크릿이 응답·입력에 평문으로 있어 서버가 실행하면 화면, 이력, LLM 경계에 남는다. 사람의 터미널에서 실행하면 시스템에 남지 않는다.
- **검토한 대안:** 처음에는 이 9개(이후 `aws eks update-kubeconfig`가 추가되어 10개, D-23)를 `restricted`(생성도 금지)로 지정했다. 사용자가 "명령어만 지원하고 실행은 직접 하게 하자"고 제안해 `manual`로 바꿨다. 금지보다 사용자 편의가 높고 안전은 동일하다.
- **감수한 비용:** 서버가 실행하지 않으므로 실행 결과의 증거가 사람이 보고한 내용뿐이다. 이력에는 누가 언제 보고했는지만 남는다. 결과 붙여넣기는 선택이다.
- **결정자:** 사용자(방식 제안), 제안→승인(결과 붙여넣기 선택, 시크릿 입력 차단).
- **대체:** `restricted`(생성 금지) 지정을 대체했다. `restricted`는 예약 종류로 남아 있다.

### D-07. 문서에 없으면 조건부 폴백 (AI 추정 표시 + 강화 승인)
- **결정:** 문서에서 근거를 못 찾으면 LLM이 추정해 명령을 만들 수 있다. 단, "AI 추정"으로 표시하고, 읽기/변경 구분 없이 항상 다른 사람의 승인을 요구하고, 이력에 폴백 플래그를 남긴다. 폴백 경로에도 허용 범위와 `manual` 거부 목록을 적용한다.
- **이유:** 사용자가 "적절한 명령어를 못 찾으면 LLM으로 진행해도 되지 않을까"라고 제안했다. 무조건 허용은 D-05의 근거 원칙을 깨고(환각 위험), 금지는 사용성을 해친다. 표시와 강화 승인으로 위험을 사람이 인지한 상태에서만 통과시킨다. 폴백 비율은 문서 보강이 필요하다는 신호로 측정한다.
- **검토한 대안:** (b) 읽기 명령에만 폴백 허용, (c) 제약 없이 자유 생성(비추천).
- **결정자:** 사용자(요청) + 제안→승인(조건부안).

### D-09. 전체 개방(0.0.0.0/0)은 허용하되 통제한다
- **결정:** 차단하지 않는다. 위험 표시, 요청자의 사유 입력, 승인자의 별도 확인, 이력 기록, 리뷰어 요약 포함을 요구하고, 사유나 확인이 없으면 실행하지 않는다. 관리 포트(22/3389)도 같은 통제를 적용하고 예외 규칙을 두지 않는다.
- **이유:** 사용자가 "필요에 따라 전체 anyopen은 필요할 수도 있다"고 했다(예: 80/443 공개). 무조건 차단하면 정당한 작업을 못 한다. 관리 포트 예외를 만들면 규칙이 복잡해지고, 같은 통제로 충분하다고 판단했다(사용자 선택 a).
- **결정자:** 사용자.

### D-11. 변경 영향을 문서에 적는다 (`impact`), 모르면 높은 위험으로 취급
- **결정:** mutate·manual 명령(77개)마다 서비스 중단 가능성, 삭제 후 재생성 여부, 되돌림 가능성, 사전 점검 읽기 명령, dry-run 방법, IaC 관리 여부, 장시간 여부를 문서에 쓴다. 영향 정보가 없는 명령(폴백 포함)은 "영향 불명"으로 높은 위험 취급한다.
- **이유:** 사용자가 "apply 전에 서비스 중단이나 삭제 후 재생성을 사전에 확인할 수 있나"를 물었다. AWS CLI와 kubectl에는 통합 plan이 없다(AWS `--dry-run`은 권한 검사일 뿐). 그래서 사람이 쓴 정적 지식 + 사전 점검 읽기 명령으로 최대한 가까이 간다.
- **한계:** 정적 지식이라 틀릴 수 있다. 진짜 "삭제 후 재생성" 판정은 IaC plan(Phase 3)의 몫이다. 핵심 명령의 `impact` 값은 팀의 검토가 필요하다.
- **참고:** `reversible` 값을 `yes/no`가 아니라 `full/partial/irreversible`로 한 것은 YAML이 `yes/no`를 불리언으로 읽기 때문이다(검증기가 잡았다).
- **결정자:** 제안→승인.

## C. 안전과 가드레일

### D-08. LLM에는 민감값을 보내지 않는다
- **결정:** 계정 ID, ARN, 리소스 ID, 액세스 키, IP/CIDR, 이메일, 리소스 이름(버킷, 클러스터, 역할 등)은 `<SG_1>` 같은 플레이스홀더로 치환해 LLM(그리고 임베딩·리랭크 같은 모든 외부 모델)에 전달한다. 매핑은 서버에만 둔다. 승인 화면과 실행 단계에서만 실제 값으로 복원한다. 이름은 정규식으로 못 찾으므로 인벤토리(알려진 이름 목록) 기반으로 치환한다. prod 대상 판별은 서버 규칙이 한다.
- **이유:** 사용자 요구("id, arn, account 등은 LLM에 전달 안 되면 좋겠다"). 이름까지 마스킹하는 이유: LLM의 역할은 의도를 명령 형태로 바꾸는 것이라 이름이 `prod-db`인지는 필요 없다. 위험도 판단(prod 여부)은 모델 추측이 아니라 서버 규칙이 더 안전하다.
- **한계:** 인벤토리에 없는 리소스 이름은 마스킹되지 않을 수 있다.
- **추가 규칙(같은 결정의 연장):** 입출력 가드레일은 필수이며 우회·완화하지 않는다(fail-closed). 사용자가 "agent가 오동작하는 부분을 최소한으로 막고 싶다"고 당부했다. 상세는 `CLAUDE.md`의 "불변 규칙".
- **결정자:** 사용자(요구, 당부), 제안→승인(이름 포함, 인벤토리).

### D-10. plan은 일괄 승인, apply는 step마다 승인, 변경 뒤 확인 step
- **결정:** plan 단계는 검토 전용(읽기 명령은 실행해 결과를 보여주고 변경은 실행하지 않음)이고 일괄 승인 후 해시로 잠근다. apply는 step마다 다른 사람이 승인하며, 변경 step마다 짝이 되는 읽기 확인 step을 실행한다. 확인이 실패하면 멈춘다.
- **이유:** 사용자가 "plan은 일괄 승인해도 되고, apply는 진행 사항별로 승인, plan에서 읽기는 실행해 결과를 알려주고, apply 때 확인하는 명령도 수행"이라고 정했다. 승인된 내용과 실행된 내용을 같게 하는 것이 핵심이다.
- **변경된 부분:** "apply 중 수정 금지"는 D-12에서 부분 재계획으로 보완되었다.
- **결정자:** 사용자.

## D. 구조, 에이전트, 검색, 평가

### D-12. 대규모 작업: phase, 게이트, 부분 재계획, poll, IaC 동기화
- **결정:** plan은 phase(단계) 구조이고 위험한 phase 앞에는 다른 사람의 게이트 확인이 필요하다(되돌릴 수 없는 step을 포함한 phase의 게이트는 제거 불가). 오래 걸리는 step은 상태 확인을 반복(poll)한다. apply 중 직접 수정은 금지하되, 일시정지 후 완료 step은 잠그고 남은 step만 새 plan 버전으로 수정·재승인할 수 있다. `iac_managed` 환경에서는 CLI 변경 뒤 코드 동기화 확인 step을 자동 추가한다. 상세는 `SERVICE.md` 3-2절.
- **이유:** EKS 1.35→1.36 업그레이드처럼 step이 많고 수십 분 걸리는 작업이 실제로 있다. 한 번의 승인으로는 부족하고, 도중에 실패하면 계획을 바꿀 수 있어야 한다. 운영 환경은 Terraform 주도이고 코드와 상태가 달라지면 안 되므로, CLI 직접 변경은 코드와 어긋난다(드리프트).
- **운영 환경(사용자 제공):** 노드는 ASG 기반 self-managed, 인프라는 Terraform 주도, kubectl 수작업은 코드와 항상 동기화. 그래서 관리형 노드그룹용 `update-nodegroup-version` 대신 ASG 인스턴스 리프레시 문서를 만들었다.
- **결정자:** 제안→승인("1~3은 진행해줘").
- **대체:** D-10의 "apply 중 수정 금지"를 부분 재계획으로 바꿨다.

### D-13. 에이전트 3종, 도구는 읽기 전용, supervisor는 Phase 2
- **결정:** 계획 에이전트(분해, 도구 호출, 명령 생성), 리뷰어 에이전트(위험·영향 요약), 실패 분석 에이전트(원인과 대안 step 제안)를 Phase 1에 둔다. 도구는 읽기 전용(문서 검색, 인벤토리 조회, 읽기 명령 실행). 에이전트는 제안만 하고 변경은 승인 엔진을 통해서만 실행된다. 서비스별 전문 에이전트 + supervisor는 Phase 2로 미룬다.
- **이유:** 처음 설계는 LLM을 두 곳(정규화, 생성)에만 쓰는 고정 파이프라인이었고, 사용자가 에이전트라 하기엔 빈약하다고 지적했다. 읽기 전용 도구와 가드가 있으면 에이전트를 강하게 써도 안전 정책이 흔들리지 않는다. supervisor는 서비스가 4개일 때 비용·지연·평가 복잡도만 늘어 과하다고 사용자가 판단했다. 대비로 문서를 서비스별로 분리하고 계획 에이전트를 인터페이스 뒤에 둔다.
- **재검토 조건:** 서비스가 약 8개 이상이거나 서비스별 정확도가 떨어질 때.
- **결정자:** 제안→승인.

### D-14. 검색: 하이브리드(RRF) + LLM 리랭크, 질의 확장은 기본 제외
- **결정:** BM25(한국어 형태소 + CLI 토큰)와 Titan 벡터를 RRF로 합치고, READ 모델(LLM)이 후보를 다시 정렬한다. 용어 사전으로 질의를 확장하지 않고, 모호 표현 탐지와 되묻기에만 쓴다. `ref/`의 크로스인코더(bge-reranker)는 쓰지 않는다.
- **이유(측정, 80 케이스, `eval/eval_retrieval.py`):**

  | 방식 | hit@1 | hit@3 | hit@5 |
  |---|---|---|---|
  | BM25 | 0.74 | 0.94 | 0.97 |
  | 벡터(Titan) | 0.65 | 0.85 | 0.91 |
  | 하이브리드 | 0.78 | 0.96 | 0.97 |
  | 하이브리드 + 리랭크 | 0.99 | 1.00 | 1.00 |

  - 벡터 단독은 BM25보다 약하고, 결합하면 좋아지며, 리랭크가 순위를 가장 크게 올렸다.
  - 용어 사전 확장은 BM25를 악화시켰다(hit@3 0.94→0.84). 문서의 키워드 줄이 이미 동의어 역할을 해서 중복이고 노이즈였다. 벡터·하이브리드에서는 이득과 손해가 엇갈렸고 차이가 케이스 2~3개 수준이라 신뢰하기 어렵다. 가장 단순한 구성(확장 없음)을 기본으로 했다.
  - 크로스인코더는 torch와 약 2GB 모델이 필요해 명령 141개 코퍼스에는 과하다. Cohere 임베딩과 Bedrock 리랭크는 이 계정에서 권한이 없다.
- **한계:** 평가셋을 문서 작성자가 만들어 낙관적일 수 있다. 실제 사용자 표현이 쌓이면 보강한다.
- **결정자:** Claude 판단 — 사용자가 "ref에 너무 엮이지 않아도 되고 더 좋은 게 있다면 그쪽으로"라고 위임했다.
- **번복:** 처음에는 질의 확장이 도움이 될 것이라 가정했으나 측정으로 반증됐다(번복 표 참조).

### D-15. 관측: Langfuse는 개발 단계 한정, 트레이스는 마스킹 경계 안쪽만
- **결정:** `TRACE_BACKEND=off|local|langfuse`, 기본 `local`. Langfuse는 개발 단계에서 명시적으로 켠 경우에만 쓴다. 트레이스에는 마스킹 이후 데이터(LLM이 보는 것)만 기록하고, 외부 전송 전에 누출 스캔을 거친다(의심 시 차단하고 로컬에만 기록).
- **이유:** 사용자가 "개발 단계에서는 Langfuse를 써도 문제없을 것 같다"고 했다. 다만 웹 요청 맨 위에서 트레이스를 걸면 마스킹 전의 실제 값이 외부로 나가므로, 기록 위치를 마스킹 이후로 못 박았다.
- **재검토 조건:** 실제 데이터를 쓰기 전에는 self-hosted로 바꾸는 것을 권장한다(마스킹 한계 때문).
- **결정자:** 사용자(허용), 제안→승인(트레이스 경계).

### D-16. 평가: 규칙 + 검색 지표 + LLM-as-Judge, RAGAS는 별도 환경
- **결정:** 규칙 기반 채점, 검색 지표(hit@k, MRR, RAGAS), LLM-as-Judge(계획 타당성)를 함께 쓴다. Judge는 생성과 다른 모델, temperature 0, 고정 루브릭이고, 수동 라벨 샘플과의 일치율을 보고한다. 평가 데이터에는 실제 값을 쓰지 않는다. RAGAS는 `.venv-eval`에서만 실행한다.
- **이유:** 사용자가 교육 과정 12개 항목 중 11(관측), 12(평가)를 추가하기로 했다. RAGAS를 설치하면 `tenacity`, `rich` 등 런타임 패키지가 다운그레이드되어 앱 환경과 분리했다(dry-run으로 확인).
- **결정자:** 사용자(11, 12 추가), 제안→승인(환경 분리, Judge 조건).
- **보완(평가셋 작성 시):** 에이전트 평가셋(`eval/agent_cases.csv`)은 실제 사용자처럼 이름을 입력해 마스킹 경로를 태워야 하고, 가드레일 시험은 비마스킹 값을 입력해야 하므로 "플레이스홀더만" 규칙을 "실제 환경의 값 금지, 합성 값(샘플 인벤토리 이름, 문서의 예시 ID) 허용, 외부·judge에는 마스킹된 형태로만"으로 명확히 했다. 허용 목록은 `tests/test_eval_cases.py`가 강제한다. 2026-11-04 사용자 승인. 승인과 함께 judge 입력 규칙을 더했다: 입력 가드가 막은 입력은 원문 대신 `[입력 차단됨: <사유 코드>]`를 보내며(`judge_view_of_input`), 합성 값 검사는 CSV 모든 열에 적용한다.

### D-17. 디렉터리: 지식 원본은 `knowledge/`, 생성물은 `data/`, 주요 문서는 루트
- **결정:**
  ```
  루트        README.md, CLAUDE.md, SERVICE.md, SPEC.md, TASK.md   주요 문서
  app/        코드
  knowledge/  직접 작성한 CLI 지식베이스(원본, 버전 관리 대상)
  data/       실행 중 생성물(벡터 색인, DB, 트레이스, 세션 작업 폴더). 지워도 재생성
  docs/       DECISIONS.md(결정과 이유), IMPLEMENTATION.md(구현 상세) + 이후 생기는 문서(런북, 회고 등)
  eval/ tests/ ref/
  ```
- **이유:** `docs/cli`는 문서가 아니라 앱이 읽는 데이터였다. 그렇다고 `data/`로 옮기면 직접 작성하는 원본과 지워도 되는 생성물이 섞여 "data는 지워도 된다"는 규칙이 깨진다. 그래서 원본은 `knowledge/`로 분리했다.
- **변천:** `docs/cli/{ec2_sg, eks_kubectl, s3, iam}` → `docs/cli/{aws/..., kubectl}`(서비스가 아니라 CLI 도구별로 나눔. `eks_kubectl`이 서로 다른 두 CLI를 섞고 `ec2_sg`는 너무 좁았음) → `knowledge/cli/`.
- **결정자:** 사용자(`knowledge/cli`로 이동, 주요 문서는 루트), 제안→승인(CLI 도구별 구조).

### D-18. Phase 구분
- **결정:** Phase 1은 로컬 + mock + 위 설계 전부. Phase 2는 이력 기반 계획 재사용(LLM 호출 최소화), 엑셀 계획서 import, 서비스별 supervisor. Phase 3는 테라큐브·GitHub PR, Terraform plan/apply 연동, AWS role 분리(plan=읽기, apply=변경), 실제 인증(SSO).
- **이유:** 사용자가 "당장 급하지 않다", "Phase 3로는 테라큐브와 GitHub PR, AWS role 설정도 해야 할 것"이라고 정했다. 테라큐브의 인터페이스는 알려지지 않아 추측하지 않고 시작할 때 설계한다.
- **결정자:** 사용자.

### D-19. Bedrock 모델 3종의 역할 매핑과 MAIN 쓰로틀링 폴백
- **결정:** `.env`의 `MAIN_MODEL`(Sonnet 4.6), `SUB_MODEL`(Sonnet 4.5), `READ_MODEL`(Haiku 4.5)을 아래처럼 쓴다. 코드에는 모델 ID를 박지 않고 `app/config.py`로 환경변수에서 읽는다.
  | 역할 | 쓰는 곳 |
  |---|---|
  | MAIN | 계획 에이전트(목표 분해, 명령 생성, 상태 기반 조정) |
  | SUB | 리뷰어, 실패 분석, LLM-as-Judge, 그리고 MAIN이 쓰로틀링일 때의 대체 |
  | READ | 가벼운 일: 질의 정규화, 범위 판단(분류), 리랭크, 긴 읽기 명령 출력의 요약(마스킹 후) |
- **MAIN 폴백:** MAIN 호출이 쓰로틀링(`ThrottlingException`, `TooManyRequestsException`, `ServiceQuotaExceededException`)이면 짧은 백오프로 재시도(최대 2회)한 뒤 SUB로 같은 요청을 보낸다. 폴백은 이 오류에만 적용하고, 스키마·검증 실패나 가드 차단에는 쓰지 않는다. 폴백해도 입력 마스킹, 누출 스캔, 명령 가드, 에이전트 한도(호출·토큰은 합산)는 그대로다. 호출 기록(트레이스·감사)에는 요청한 역할과 실제로 쓴 역할을 함께 남긴다. SUB도 쓰로틀링이면 계속하지 않고 중단해 사람에게 알린다. READ로는 폴백하지 않는다(계획·리뷰에는 약하다).
- **이유:** 사용자 지시(2026-11-04): MAIN이 쓰로틀링에 걸리면 SUB로 진행하고, READ는 가벼운 에이전트에 붙인다. 계획 품질이 가장 중요한 MAIN 호출이 병목이 되어도 작업이 멈추지 않게 하되, 폴백이 가드를 우회하는 경로가 되지 않게 범위를 오류 종류와 방향(MAIN→SUB 한 방향)으로 한정했다.
- **영향:** Judge는 생성한 모델과 다른 모델을 써야 하므로(SPEC 34), 평가는 기록된 실제 생성 모델을 보고 반대쪽(SUB가 생성했으면 MAIN)을 judge로 고른다. 폴백이 잦으면 평가 결과를 모델별로 나눠 본다.
- **검토한 대안:** 폴백 없이 대기·실패(작업이 멈춤), 폴백 대상에 READ 포함(계획 품질 저하), 모든 오류에 폴백(검증 실패를 가려 오동작을 숨김).
- **결정자:** 사용자(폴백 방식과 READ 용도 지시), 세부(오류 종류, 재시도 2회, 출력 요약 용도)는 제안→승인(2026-11-04 확정). 구현은 `app/llm.py`, 리랭크의 READ 사용은 측정됨.

### D-20. 문서 체계: README는 루트, 결정 기록은 `docs/`, 작성 규칙은 `CLAUDE.md`
- **결정:** 서비스 소개와 실행 방법을 담은 `README.md`는 루트에 둔다. 주요 문서 `CLAUDE.md`, `SERVICE.md`, `SPEC.md`, `TASK.md`도 루트에 둔다. 결정 기록 `DECISIONS.md`와 구현 상세 `IMPLEMENTATION.md`는 `docs/`에 둔다. 문서를 어떻게 쓰고 어디에 두는지에 대한 규칙은 `CLAUDE.md`에 쓴다.
- **이유:** git에 올리면 루트의 `README.md`가 저장소 첫 화면에 보이므로 서비스 설명과 실행 방법이 거기 있어야 한다. 작성 규칙은 Claude Code가 항상 읽는 `CLAUDE.md`에 있어야 지켜진다. 결정 기록은 계속 쌓이는 문서라 루트를 어지럽히지 않도록 `docs/`에 둔다.
- **변천:** `docs/README.md`(폴더 용도 설명)를 만들었다가 루트 `README.md`로 바꿨다. `DECISIONS.md`는 처음 루트에 있었다(주요 문서는 루트라는 원칙). 사용자가 `docs/`가 낫다고 해서 옮겼다. 이후 `SERVICE.md`가 193줄로 커져 구현 상세(가드 구현, 검색 구성, 관측·평가)를 `docs/IMPLEMENTATION.md`로 분리했고, 문서 사이의 관계 설명은 `CLAUDE.md`의 문서 체계 표에만 두기로 했다(사용자 제안). 정책 본문의 중복도 정리했다: 가드레일 규칙은 `CLAUDE.md`가 본문을 갖고 `SERVICE.md` 6절은 서비스가 보장하는 것만 요약하며, 대규모 작업·운영 환경은 `SERVICE.md`가 본문을 갖고 `CLAUDE.md`는 불변 조건과 링크만 둔다. 정책이 바뀌면 두 문서를 함께 고치는 규칙은 그대로다. 스택은 표(사용 중/예정 현황)만 `SERVICE.md`에 두고, 스택 제약("범위 안에서 쓰고 임의로 늘리지 않는다")은 동작을 좌우하므로 `CLAUDE.md`에 한 줄 둔다. `CLAUDE.md`는 매 세션 컨텍스트로 로드되므로 불변 조건만 한 줄씩 두고 세부 규칙과 목록은 `docs/IMPLEMENTATION.md`로 옮겼다(사용자 요청: 문서가 크다). 단, 1차 정리는 "지운 구절이 다른 문서에 있는가"만 확인해 제 동작을 좌우하는 규칙(간접 인젝션 무시, 되묻기, 전체 개방 통제, 샌드박스, 트레이스 경계 등)이 자동 로드되는 `CLAUDE.md`에서 빠졌다. 사용자가 "지워도 동작이 달라지면 안 된다"고 지적해 복구했고, 이후 `CLAUDE.md`를 줄일 때는 "`CLAUDE.md`만 읽고 같은 동작을 하는가"로 확인하는 규칙을 문서 작성 규칙에 넣었다.

### D-22. 가드는 마스킹 전후 두 단계로 판단한다
- **결정:** 구조 검사(셸 연산자, 옵션, 플레이스홀더)는 마스킹된 명령으로 하고, 위험 판단(관리형 정책 이름, 정책 파일 내용, prod 대상)은 서버 안에서 복원한 실제 값으로 한다. 복원한 값은 판정 결과, 로그, 오류 어디에도 담지 않는다. AWS 관리형 정책 ARN(`arn:aws:iam::aws:policy/...`)은 공개 값이라 마스킹하지 않는다.
- **이유:** 모델이 만든 명령에는 플레이스홀더만 있다. `<POLICY_ARN_1>`만 봐서는 `AdministratorAccess`인지 알 수 없고 `<BUCKET_2>`가 prod인지도 알 수 없다. 위험 판단을 마스킹된 값으로만 하면 가장 중요한 위험을 놓친다. 복원은 서버 안에서만 일어나므로 모델 경계(D-08)는 그대로 지켜진다. 관리형 정책 ARN을 마스킹하면 모델이 `AdministratorAccess`와 `ReadOnlyAccess`를 구분하지 못해 계획 자체를 못 만든다.
- **검토한 대안:** 마스킹된 값만으로 검사(위험을 놓침), 모델에 정책 이름만 별도 힌트로 제공(경로가 늘고 복잡).
- **결정자:** Claude 판단(설계).

### D-23. 명령 허용 범위와 금지 목록
- **결정:**
  - CLI는 `aws`와 `kubectl`만. 셸 연산자(`;` `|` `&&` `>` 등), 명령 치환, 환경변수 확장, 여러 줄은 막는다.
  - 문서에 없는 명령(폴백, D-07)도 문서에 있는 AWS 서비스(ec2, eks, s3, s3api, iam, autoscaling, ssm)에서만 허용한다. 서비스를 넓히려면 문서를 추가한다.
  - 대상·자격증명을 바꾸거나 숨은 입력을 읽는 옵션은 금지한다: `--profile`, `--endpoint-url`, `--no-verify-ssl`, `--debug`, `--cli-input-json`, `--kubeconfig`, `--context`, `--token`, `--as`, `--raw` 등.
  - 문서에 없더라도 비밀값을 만들어 내거나 인스턴스에서 임의 명령을 실행하는 작업은 거부한다(`ec2 get-password-data`, `create-key-pair`, `eks get-token`, `ssm send-command` 등).
  - `kubectl delete -A`는 차단하고, `--all`과 네임스페이스 삭제는 강한 경고로 둔다. 넓은 CIDR은 전체 개방(D-09)은 아니지만 강한 경고다: `/7` 이하는 항상, 그 밖에는 사설(RFC1918: 10/8, 172.16/12, 192.168/16)이 아닌 `/16` 이하(공인 대역의 넓은 범위). 사설 대역 서브넷은 경고하지 않는다. 서버 전역 kubeconfig를 바꾸는 `kubectl config` 하위 명령(use-context, set-context, set-cluster, set-credentials, set, unset, delete-context/cluster/user, rename-context)은 차단(`kubeconfig_mutation`)하고, `aws eks update-kubeconfig`는 `manual`로 바꿨다(전역 `~/.kube/config`를 수정하므로 서버가 실행하지 않는다). `kubectl`의 대화형 옵션(`--stdin --tty`)은 `manual` 명령(D-06)만 쓸 수 있다.
  - 문서에 없는 kubectl 명령은 내장 명령일 때만 도움말을 읽는다(플러그인 차단).
- **이유:**
  - 옵션 금지: mock 모드는 환경변수로 엔드포인트와 더미 키를 강제한다(D-04). 모델이 `--endpoint-url`이나 `--profile`로 덮어쓰면 실제 AWS로 나갈 수 있다. `--context`는 대상 클러스터를 바꾸므로, 대상은 계획의 사전 점검 step(현재 컨텍스트 확인)으로 고정한다.
  - 폴백 서비스 범위: D-07이 폴백을 허용했지만 어떤 서비스든 만들게 하면 범위를 확인할 수 없다. 문서가 곧 범위다.
  - 셸 연산자: 실행기는 셸을 쓰지 않지만 파이프와 리다이렉트는 의도가 모호하고 우회 통로가 된다.
  - 플러그인: `kubectl <이름> --help`를 읽는 것만으로 설치된 플러그인 실행 파일이 실행된다. 자체 점검에서 발견했다.
- **검토한 대안:** 옵션을 허용 목록으로 관리(CLI 옵션이 수백 개라 불가능) → 대신 "실제 CLI에 있는 옵션에서 금지 목록을 뺀 것"을 허용한다. 금지 목록은 새 위험 옵션을 놓칠 수 있으므로 정기 점검이 필요하다.
- **재검토 조건:** `--context` 금지는 여러 클러스터를 다루는 작업이 생기면(Phase 3, 인벤토리로 검증된 context만 허용) 다시 본다. 실행기는 요청(세션)별로 격리된 kubeconfig·자격증명을 쓴다는 계약만 두고 구현은 실행 위치(D-28)에 따라 정한다.
- **결정자:** 제안→승인(2026-11-04 사용자 검토 후 승인: 금지 옵션 목록, 폴백 서비스 범위, 거부 작업 유지, `--context` 금지 유지, 위 CIDR·kubeconfig 보강 반영).

### D-24. 시크릿은 마스킹이 아니라 차단한다
- **결정:** 비밀번호, 키, 토큰, 개인키, JWT, presign URL의 서명이 입력에 있으면 마스킹하지 않고 입력을 막는다. 실행 결과에서는 이런 값을 LLM으로 돌려보내기 전에 제거한다. 시크릿이 나올 수 있는 경로를 막는다: `kubectl get secret -o yaml/json/jsonpath`(파일 지정 포함), `kubectl create secret`, SSM은 `/aws/service/` 공개 경로만 읽고 복호화 금지. `create-login-profile`의 `--password`는 `<PASSWORD>` 자리 표시만 허용한다.
- **이유:** 계정 ID나 이름은 "모델이 몰라도 되는 값"이라 치환하면 되지만, 시크릿은 시스템에 들어오는 것 자체가 문제다. 치환해도 복원하려면 어딘가에 평문으로 보관해야 한다. D-06의 `manual` 명령이 같은 이유로 시크릿을 사람의 터미널에 남긴다.
- **한계:** 패턴 기반이라 완전하지 않다. 예를 들어 파드 환경변수의 `name: DB_PASSWORD` / `value: …` 형식은 못 잡는다.
- **결정자:** 제안→승인(2026-11-04 검토 후 유지).

### D-25. 감사 기록은 입력 텍스트를 저장하지 않는다
- **결정:** 가드 판정 기록에는 단계, 허용 여부, 사유 코드, 입력의 길이와 HMAC-SHA256(설치별 무작위 키, 앞 12자)만 남긴다. 시크릿 차단 입력(`secret_in_input`)은 해시도 남기지 않는다. 입력 텍스트(마스킹된 형태도)는 저장하지 않는다.
- **이유:** 차단된 입력에는 시크릿이 들어 있을 수 있다. 마스킹된 텍스트를 저장하는 방식은 마스킹이 실패한 바로 그 경우에 원본이 남는다. 키 없는 SHA-256 앞 12자는 입력 템플릿을 알면 오프라인 대입으로 값을 확인할 수 있어(검토에서 확인) 키 있는 HMAC으로 바꿨다. 키는 DB 밖 파일(`data/audit.key`, 명시한 DB 경로는 `<db>.key`)에 둔다. 같은 설치에서는 같은 입력을 연결할 수 있어 감사에는 충분하다. 요청 내용 자체는 허용된 것에 한해 plan 이력(T7)에 마스킹된 형태로 남는다.
- **검토한 대안:** 마스킹된 텍스트 저장(마스킹 실패 시 유출), 모든 입력에 키 없는 해시(추측 가능), 해시 완전 제거(같은 입력 연결 불가).
- **결정자:** 제안→승인(2026-11-04).

### D-27. 웹·저장 스택: FastAPI + WebSocket + 단일 HTML/JS + SQLite
- **결정:** 서버는 FastAPI(uvicorn), 두 사람의 실시간 공유는 WebSocket, UI는 빌드 도구 없는 단일 HTML/JS 페이지, 저장은 SQLite다. 나머지 스택(Python, Bedrock, LangChain/LangGraph, Chroma)은 `ref/`의 교육 예제 스택을 참고한다. 현재 사용 현황은 `SERVICE.md` 1-1절.
- **이유:** Python 하나로 LangGraph 에이전트와 같은 프로세스에서 돌고 로컬에서 바로 실행된다. 링크 초대, 요청자·승인자 구분, 실시간 동기화, 승인 UI는 직접 만들어야 하는 협업 기능이라 프레임워크가 정해 둔 화면보다 자유로운 구성이 맞다. SQLite는 `langgraph-checkpoint-sqlite`와 같은 저장소라 일시정지·재개(D-12의 부분 재계획)와 감사 기록(D-25)을 한 곳에 둘 수 있다.
- **검토한 대안:** Streamlit/Gradio(빠르지만 두 사람의 실시간 동기화와 승인 UI를 만들기 어렵다), React 프런트엔드(UI는 좋아지나 빌드 환경이 늘어 mock 단계에는 과하다).
- **재검토 조건:** 사용자가 늘거나 UI가 복잡해지면 프런트엔드를 분리한다. 서버를 여러 대로 늘리면 SQLite를 교체한다.
- **참고:** 기록이 늦었다. 이 결정은 초반 인터뷰에서 정했고(사용자: "추천대로 진행") 문서 체계를 정리하는 중에 `DECISIONS.md`에 빠진 것을 발견해 추가했다.
- **결정자:** 사용자(`ref/` 참고 요청: "개발 스택은 ref 디렉토리를 참고해서 진행해보자"), 제안→승인(웹 스택).

### D-28. 실행 위치: 이 서버가 직접 실행 vs 권한 있는 서버에 요청 (미정)
- **상태:** 미정(2026-11-04 사용자: "내 서버가 직접 날릴지, 권한이 있는 서버에 요청을 보내서 할지 아직 정해지지 않았다").
- **지금 정한 것(어느 쪽이든 유효한 계약):**
  - 실행기는 `executor/base.py` 인터페이스 뒤에 두고, 실행 요청은 직렬화 가능한 `ExecutionRequest`(마스킹 이전 값 복원 후의 명령, 세션·plan·step id, 타임아웃)로 만든다.
  - kubeconfig·자격증명은 요청(세션)별로 격리한다. 서버 전역 `~/.kube/config`나 현재 context를 바꾸지 않는다. 그래서 `kubectl config` 변경 하위 명령은 차단하고 `aws eks update-kubeconfig`는 `manual`이다(D-23).
  - 자격증명은 실행하는 호스트에만 있다. 이 앱 서버와 모델 쪽에는 두지 않는다.
  - 가드(`CommandGuard.check`, `assert_server_executable`)는 승인 서버에서 한 번, 실행하는 쪽에서 다시 한 번 적용한다(이중 확인).
- **선택지와 영향:**
  | | 이 서버 직접 실행 | 권한 서버에 요청 |
  |---|---|---|
  | 로컬 경로(`file://`, `s3 cp`) | 세션 작업 폴더 샌드박스로 충분 | 파일 내용을 요청에 실어 보내거나 원격 쪽 작업 폴더를 정해야 함 |
  | 자격증명 | 이 서버에 role이 필요 | 원격 호스트만 보유, 이 서버는 요청 권한만 |
  | 격리 kubeconfig | 이 서버가 세션별 임시 파일을 만듦 | 원격 호스트가 요청별로 만듦 |
  | 감사 | 한 곳 | 요청·결과 양쪽 기록과 연결 id 필요 |
- **결정 시점:** T5(실행기) 시작 전. 실행기 구현은 이 결정 후에 한다.
- **결정자:** 미정(사용자 결정 사항).

### D-29. 마스킹 매핑은 세션별로 암호화해 SQLite에 저장한다 (서버 재시작 후 이어가기)
- **결정:** 플레이스홀더와 실제 값의 매핑(`Masker`의 상태)을 세션 단위로 AES-256-GCM 암호화해 SQLite(`data/mapping.sqlite`)에 저장한다. 키는 DB 밖 파일(`data/mapping.key`, 감사 HMAC 키와 별도)에 둔다. 세션 id를 AAD로 묶어 다른 세션의 암호문으로 바꿔치기할 수 없게 하고, 마지막 갱신 후 24시간(TTL)이 지나거나 apply가 끝나·취소되면 삭제한다. 복호화에 실패하면 "없음"이 아니라 오류로 멈춘다(fail-closed). 저장소는 `MappingStore` 인터페이스 뒤에 둔다. 로그·트레이스·모델에는 계속 마스킹된 형태만 간다.
- **이유:** 사용자가 서버 재시작 후에도 apply를 이어가길 원했다(2026-11-04). 매핑을 메모리에만 두면 재시작 때 사라진다. 인벤토리로 재구성하는 방식은 인벤토리에 없는 값(사용자가 입력한 ID 등)을 복원하지 못해 승인된 plan이 실행 불가가 될 수 있다. 시크릿은 마스킹 대상이 아니라 입력에서 차단되므로 이 매핑에 들어가지 않는다.
- **검토한 대안:** 메모리만(재시작 시 소실), 인벤토리로 재구성(복원 범위 부족, 가장 작은 구현이라 초기에 추천했으나 이어가기 요구로 대체), 평문 SQLite(DB 유출 시 노출), Redis(TTL·다중 서버 공유는 이점이나 새 인프라와 스택 승인이 필요하고, 영속화하면 어차피 암호화가 필요하며 SQLite와 이중 저장소가 된다).
- **한계:** 서버가 침해되어 키 파일과 DB를 함께 읽히면 값이 노출된다. 로컬 1인 검증 단계에서는 허용하고 운영 전환 때 KMS·시크릿 매니저로 옮긴다.
- **재검토 조건:** 서버를 여러 대로 늘리거나 D-28에서 "권한 서버에 요청"으로 정해지면 Redis 구현을 `MappingStore`에 추가하는 것을 검토한다. 이 결정으로 새 패키지 `cryptography`가 들어온다(사용자 승인).
- **구현:** `app/guards/mapping_store.py`, `keyfile.py`, `Masker.export_state/load_state`, `tests/test_mapping_store.py`. 세션·apply 흐름과의 연결(저장 시점 호출, 종료 시 삭제)은 T6/T7.
- **결정자:** 제안→승인(2026-11-04).

### D-30. 모호한 표현은 모델이 근거로 해소하고 서버가 검증하며, 근거가 없으면 되묻는다
- **결정:** 모호한 표현의 탐지는 서버(용어 사전 `ambiguous`)가 한다. READ 모델은 요청 문장 안의 근거로 후보 중 하나가 분명한지만 답한다(`{alias, choice, evidence, confidence}`). 서버는 (1) 후보가 사전 목록 안에 있고 (2) 근거 인용이 마스킹된 요청에 실제로 들어 있고(별칭 자체는 근거가 아님) (3) 확신도가 높을 때만 해소로 인정한다. 하나라도 어긋나면 사용자에게 되묻는다. 모델은 사전에 없는 표현을 해소 대상으로 만들 수 없다. 해소한 해석은 사용자에게 보여 주고 이력에 남기되, 별도 예/아니오 확인은 받지 않는다. 확인은 두 사람의 plan 검토가 맡고, 해석이 틀리면 후보 중 다른 해석으로 다시 만든다.
- **이유:** 문맥으로 분명한 경우(`can-i` 같은 구문이 있는 권한 확인 요청)까지 매번 되물으면 번거롭다(사용자 지적, 2026-11-04). 반면 모델이 자유롭게 고르면 틀린 해석이 조용히 퍼진다. 이전 측정에서 `서버`를 EC2로 자동 확장했을 때 검색이 나빠졌다(D-14). 그래서 선택권은 모델에, 판정은 서버에 둔다. 모델이 틀려도 서버 검증을 통과하려면 요청에 있는 근거가 필요하고, 변경은 plan 승인 전에는 실행되지 않으므로 잘못된 해석의 비용은 계획 재생성에 그친다.
- **검토한 대안:** 항상 되묻기(안전하지만 번거로움, 이전 규칙), 모델이 검증 없이 해소(틀린 해석이 숨음), 변경 의도일 때 해소돼도 예/아니오 확인(제안했으나 사용자가 번거롭다고 판단해 제외).
- **한계:** 근거 구절이 요청에 있어도 해석이 틀릴 수 있다(예: 문장 일부만 근거). 평가셋 케이스 25·26·41·42로 측정하고, 틀린 해소가 잦으면 확신도 기준이나 변경 의도 확인을 다시 검토한다.
- **구현:** `app/planner/intake.py`(`Intake`), `tests/test_intake.py`. 입력 가드가 막은 요청에는 모델을 부르지 않고, 모델 출력(정규화 질의·되묻기 문장)은 누출 검사 후 사용하며, 스키마 오류는 재시도 후 사람에게 넘긴다.
- **결정자:** 사용자 제안(되묻기 전에 모델로 해소), 서버 검증 조건과 변경 의도 확인 제외는 제안→승인(2026-11-04).

### D-31. 서버·노드는 항상 EC2 인스턴스, Pod은 Pod이다 (모호 표현이 아니다)
- **결정:** 사용자가 말하는 "서버"와 "노드"(워커 노드 포함)는 항상 EC2 인스턴스로 본다. Pod은 Pod이다. 이 둘은 되묻거나 모델의 해소(D-30) 대상으로 삼지 않는다. 노드를 쿠버네티스에서 다루는 작업(`drain`, `cordon`, `top node`)은 같은 인스턴스를 k8s Node 객체로 보는 것이라 되묻지 않고 동작에 맞는 CLI(kubectl 또는 aws)를 고른다. `glossary.yaml`의 `ambiguous`에서 `서버`를 뺐고, 한글 `노드`·`워커 노드`는 EC2 항목과 kubectl Node 항목 양쪽의 별칭으로 둔다. 접수 프롬프트에 고정 사실로 넣고, 노드의 상태·스케줄링·리소스는 kubectl, 인스턴스 자체(상태 점검·재부팅·종료·ASG)는 aws로 간다고 적었다. `노드 상태 확인해줘`가 EC2로만 가지 않도록 검색 평가셋에 r81~r85를 추가해 확인했다(기본 구성에서 `kubectl get`이 1위, 2026-11-04 해당 6개 질의 직접 확인. 전체 평가 재측정은 하지 않았다).
- **이유:** 사용자 지시(2026-11-04: "서버나 노드는 EC2고, pod는 pod야. 헷갈리면 안 돼"). 운영 환경이 ASG self-managed 노드라 노드가 곧 EC2 인스턴스다(`SERVICE.md` 3-3절). 혼동할 여지가 없는 용어를 되물으면 번거롭고, 모델이 `서버`를 Pod으로 해소하면 틀린 계획이 나온다.
- **검토한 대안:** 되묻기(번거롭고 불필요), 문맥으로 해소(D-30, 혼동 가능성이 없는 용어에는 과함).
- **재검토 조건:** 매니지드 노드그룹이나 Fargate를 쓰게 되어 노드가 EC2가 아닐 수 있을 때.
- **구현:** `knowledge/cli/glossary.yaml`, `app/planner/intake.py` 프롬프트, `tests/test_intake.py`·`tests/test_rag.py`의 회귀 테스트, 평가셋 26·41·42번과 검색 평가 r14 태그 갱신.
- **결정자:** 사용자.
